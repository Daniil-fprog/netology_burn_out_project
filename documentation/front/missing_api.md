# Чего не хватает в API для нового фронтенда

Фронтенд (`frontend/app`) уже работает со всеми страницами из ТЗ. Там, где в backend нет нужного эндпоинта или поля, фронт ходит в заглушку. Заглушка повторяет адреса и формат ответов backend, поэтому после доработок фронт менять не придётся — достаточно собрать его в режиме `real`.

Эталонная реализация каждого пункта — в `frontend/app/src/api/mock/router.js` (поиск по адресу маршрута). Там же видны проверки прав и коды ошибок, которые ожидает фронт.

Общие правила, как в остальном API:

- все запросы с `Authorization: Bearer <token>`;
- ошибки — `{"detail": "текст для пользователя"}`, фронт показывает `detail` как есть;
- списки — `{"page", "page_size", "total", "items"}`, параметры `page` и `page_size`;
- даты — `YYYY-MM-DD`, время — ISO 8601 **с часовым поясом** (см. раздел 4).

Приоритеты: **П1** — без этого не работает вход и ввод факта; **П2** — страницы руководителя; **П3** — администрирование и выгрузки.

## 1. Новые эндпоинты

### П1. `GET /api/v1/me/access` — роли и школы текущего пользователя

`/users/me` не отдаёт роли, школы и связь с педагогом, а без них фронт не знает, какие разделы показывать и какой `school_id` подставлять в запросы. Можно вместо отдельного эндпоинта добавить эти поля в `/users/me`.

```json
{
  "roles": ["teacher"],
  "schools": [
    { "id": "S101", "name": "МБОУ «Школа № 101»", "external_code": "DEMO-SCHOOL-101", "teacher_id": "T002" }
  ]
}
```

`teacher_id` — карточка педагога этого пользователя в школе, `null` для руководителей. Для `group_head` в `schools` — все школы его групп.

### П1. `POST /api/v1/schools/{school_id}/workload/daily` — создать день

Сейчас факт можно только изменить через `PATCH .../daily/{record_id}`, а `record_id` есть, только если журнал за день уже создан. Учитель не может заполнить день, на который нет журнала, — например, работу в выходной без плана.

Тело — как у `PATCH`, плюс дата:

```json
{
  "work_date": "2026-11-08",
  "day_type": "Выходной",
  "status": "draft",
  "comment": null,
  "entries": [
    { "planned_work_item_id": null, "work_type_id": "WT4", "duration_hours": 2, "location": "home", "comment": null }
  ]
}
```

Ответ — строка в формате `GET .../daily` (см. раздел 2). Ошибки: `422` за будущую дату, `409` если журнал за эту дату уже есть, `403` если у пользователя нет карточки педагога в школе.

### П2. `GET /api/v1/schools` — школы пользователя со сводкой

Для карточек на странице «Школы и педагоги».

```json
[
  {
    "id": "S101", "name": "МБОУ «Школа № 101»", "external_code": "DEMO-SCHOOL-101",
    "group": "Северный округ", "teacher_count": 6, "linked_accounts": 1, "director_name": "Кузнецов Андрей М."
  }
]
```

`linked_accounts` — сколько педагогов связано с учётной записью.

### П2. `GET /api/v1/schools/{school_id}/workload/plan-items` — план построчно

Таблица на «Управлении планом». `GET .../daily` отдаёт только суммы по видам работ, а нужна каждая плановая работа отдельно.

Параметры: `teacher_id`, `work_type_id`, `date_from`, `date_to`, `page`, `page_size`. Роли: директор, глава, глава группы.

```json
{
  "page": 1, "page_size": 20, "total": 171,
  "items": [
    {
      "id": "P101", "plan_version_id": "PV1", "plan_version": 2, "source_import_filename": "plan_nov_w2.xlsx",
      "teacher_id": "T002", "work_type_id": "WT1", "work_date": "2026-11-09", "day_type": "Учебный день",
      "subject": "Русский язык", "duration_hours": 3.0, "sequence_no": 1, "comment": null
    }
  ]
}
```

Сортировка: дата, педагог, `sequence_no`.

### П3. Очередь выгрузок (`export_jobs` из ТЗ)

Страница «Отчёты и экспорт». Отчёт ставится в очередь, фронт опрашивает список раз в 3 секунды, пока есть отчёты в статусе `running`.

**`POST /api/v1/exports`**

```json
{
  "report": "plan_vs_fact",
  "school_ids": ["S101", "S102"],
  "teacher_id": null,
  "date_from": "2026-10-19",
  "date_to": "2026-11-15",
  "format": "xlsx"
}
```

Отчёты и роли, которым они доступны:

| `report` | Что | Роли |
|---|---|---|
| `plan` | план и нормы | teacher (только свой), director, head, group_head |
| `plan_vs_fact` | план против факта по дням и видам работ | teacher (свой), head, group_head |
| `summary` | недельные и месячные сводки | head, group_head |
| `surveys` | оценки анкет по шкалам, без текстов | teacher (свои), head, group_head |
| `imports` | история импортов | director, head, group_head |
| `audit` | журнал аудита | head, group_head |
| `ml_dataset` | псевдонимизированный датасет, только CSV | head, group_head |

Ответ — задание: `{"id", "report", "params": {...}, "status": "running", "created_at", "expires_at": null}`. `403` если отчёт не разрешён роли или школа вне области.

**`GET /api/v1/exports`** — свои задания, новые сверху, с пагинацией. Статусы: `running`, `ready`, `expired`, `failed`. У `ready` заполнен `expires_at` (во фронте написано «хранятся 7 дней»).

**`GET /api/v1/exports/{id}/file`** — сам файл.

Существующие `GET .../workload/exports`, `.../surveys/exports` и ML-датасет можно использовать внутри как генераторы файлов.

### П3. Пользователи и права (только `system_admin`)

Страница «Пользователи и права». Сейчас есть только `POST /schools/{id}/access`.

**`GET /api/v1/admin/users`** — параметры `q` (имя или логин), `role`, `status` (`active` / `blocked`), пагинация.

```json
{
  "id": 3, "name": "Лебедева Наталья О.", "login": "head", "is_active": true,
  "role": "head", "school_ids": ["S101", "S102"], "group_ids": [],
  "teacher": null, "scope_label": "Школа № 101, Школа № 102", "updated_at": "2026-09-01T09:13:00+03:00"
}
```

`teacher` — `{"id", "full_name", "school_id"}` для преподавателя, связанного с карточкой. `scope_label` — готовая подпись области для таблицы.

**`PUT /api/v1/admin/users/{id}/access`** — назначить роль и область одним запросом:

```json
{ "role": "teacher", "school_ids": ["S102"], "group_ids": [], "teacher_id": "T101" }
```

Проверки, которые ждёт фронт (`422` / `409` с понятным `detail`):

- `director` и `teacher` — ровно одна школа;
- `head` — хотя бы одна школа;
- `group_head` — хотя бы одна группа, школы берутся из групп;
- `teacher` — карточка педагога из этой школы; если карточка уже связана с другим пользователем — `409`.

Ответ — пользователь в формате списка. Каждое изменение пишется в аудит.

**`POST /api/v1/admin/users/{id}/block`** — тело `{"unblock": false}` блокирует, `{"unblock": true}` разблокирует. Себя заблокировать нельзя (`422`). Заблокированный пользователь при входе получает `403` «Вход заблокирован администратором».

**`POST /api/v1/admin/users`** — создать учётную запись `{"name", "login"}`, роль назначается отдельно. `409` если логин занят.

**`GET /api/v1/admin/users/{id}/audit`** — журнал назначений: `[{"id", "at", "actor", "text"}]`, новые сверху.

**`GET /api/v1/admin/schools`** — школы с педагогами для выбора карточки: `[{"id", "name", "teachers": [{"id", "full_name", "user_id"}]}]`.

**`GET /api/v1/school-groups`** — группы школ: `[{"id", "name", "school_ids"}]`.

## 2. Поля, которых не хватает в существующих ответах

### П1. `GET .../workload/daily` — построчные данные дня

Сейчас в строке только суммы `planned_<код>_hours` / `actual_<код>_hours`. Форме «Моя нагрузка» нужна каждая работа отдельно — чтобы показать строку на каждую плановую работу и отредактировать факт по ней.

```json
{
  "plan": { "...": "как сейчас", "items": [ { "id": "P101", "work_type_id": "WT1", "duration_hours": 3.0, "sequence_no": 1, "subject": "...", "comment": null } ] },
  "actual": {
    "...": "как сейчас",
    "updated_at": "2026-11-10T21:00:00+03:00",
    "entries": [ { "id": "E1", "planned_work_item_id": "P101", "work_type_id": "WT1", "duration_hours": 3.0, "location": "school", "comment": null } ]
  }
}
```

`updated_at` нужен для подписи «Изменено …» и для `If-Match` (сейчас `PATCH` сверяет `updated_at.timestamp()`, но фронту это значение негде взять). Комментарии в `entries` — только владельцу, как сейчас с `actual.comment`.

### П1. `GET .../teachers` — ФИО и поиск

- `full_name` — без него таблицы педагогов показывают только `external_id`;
- `has_account` — связана ли карточка с учётной записью (страница «Школы и педагоги»);
- параметр `q` — поиск по ФИО и предмету;
- параметр `only_active=true` — только работающие.

### П2. `GET .../workload/imports` — автор импорта

`created_by_name` — имя пользователя для колонки «Пользователь» в истории импортов.

## 3. Ошибки, найденные при подключении

1. **Дашборд: отклонение от нормы в разных единицах.** В `analytics_service.get_planned_dashboard` `deviation_from_norm_hours = planned_teaching - expected`, где `planned_teaching` — обычные часы из `duration_hours`, а `expected = contract_teaching_hours_per_week × недели` — академические часы по договору. Педагог с точным выполнением договора получает отрицательное отклонение (на 18 уч.ч/нед за 4 недели: 54 − 72 = −18). Нужно `expected × 0.75` или сравнивать в академических часах. Фронт сейчас считает отклонение сам и это поле не использует.
2. **Время без часового пояса.** `submitted_at`, `imported_at` и другие отдаются без зоны (`2026-11-10T18:30:00`). Если это UTC, браузер покажет время на 3 часа раньше. Нужно отдавать с зоной (`...+03:00` или `...Z`).

## 4. Вопросы

1. **Ноль часов.** `duration_hours` должен быть больше 0, поэтому «работу не выполнял» нельзя сохранить как 0. Фронт сейчас не отправляет такие строки, и у завершённого дня пустая строка показывается как 0, у черновика — как «нет данных». Так и оставить?
2. **Ручное изменение плана.** По ТЗ директор и главы могут править план, в API есть только импорт Excel. Во фронте ручной правки пока нет — нужна ли она в этой версии?
3. **Коэффициенты сложности.** `complexity_weight` — веса 0–1 с суммой 1, в расчётах пока не участвуют. Страница «Виды работ» показывает их как есть и подсвечивает, если сумма не 1. Если перейдём на множители «1,0 = обычная работа», на фронте поменяются только подписи.

## Как проверить фронт с backend

```bash
cd frontend/app
npm install
VITE_API_MODE=real npm run dev
```

Фронт откроется на http://127.0.0.1:5173 и будет ходить в backend на `localhost:8000` через прокси Vite. В Docker: `docker compose up --build`, фронт на http://localhost:8080, Nginx проксирует `/api/` и `/users/` в backend.
